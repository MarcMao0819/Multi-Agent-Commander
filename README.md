# Multi-Agent-Commander

**让一个 AI 当舰长，指挥仍留在原生终端或应用里的 agent，把任务从派出推进到验收。**

不是把模型 API 接到同一个聊天框里，也不要求把模型反代到一个统一端点。舰员继续使用各自工具的会话、工作目录和权限；舰长按可用通道派任务，靠任务书、回执和实物证据交接，而不是靠自己转述一切。**接管一个已打开的终端或应用，需要相应投递通道，不能因它支持某个模型就视为已接入。**（[总规程][S1]、[终端投递规格][S2]）

本项目原名 **StarFix（牵星）**，现名 **Multi-Agent-Commander**。当前交付是**规程 + 模板 + 支撑脚本 + 部分适配候选**，不是开箱即用、全平台统一运行的产品。（[原首页][S0]）

## 解决什么问题

几个 agent 能同时干活，不代表一队 agent 能长期交付：

- **上下文一换，没人知道上次做到哪。** 把任务、阻塞、判据、交接卡放到文件里，让接任者有东西可读。
- **窗口很多，派错人、投错窗、消息没提交。** 先辨认会话与投递通道，区分忙、草稿、未确认，不能把“写进输入框”当成送达。
- **自报完成，却没有独立验收。** 承建、复审分开；回执附证据，舰长根据实物作验收决定。
- **人变成消息中转站。** 把确需人定的问题收敛成带推荐项的确认题，答复关联到被阻塞的任务。（[总规程][S1]、[终端投递规格][S2]、[激活器规格][S3]）

适合多条线并行、持续数日或更久、可能换会话或换工具的项目。只有一个短任务、一个执行者时，这套登记与监听的成本未必值得。（[原首页][S0]）

### 不是什么

- 不是模型 API 聚合、代售 token 或统一反代服务。
- 不是替代 Claude Code、Codex、OpenCode、Cursor 等工具本身。
- 不是读取所有应用内部状态或隐藏思维链的万能监视器；这里可核实的“工作逻辑”是任务、分工、依赖、公开进展、回执和验收依据。
- 不是无限授权自动上线；投递权限不等于生产、发布或外部系统写入权限。
- 不是已经发布的全平台可写驾驶舱。仓库当前的舰队看板是**只读**的。（[总规程][S1]、[终端投递规格][S2]、[只读看板说明][S4]）

## 谁负责什么，事实放在哪里

| 角色 | 负责 | 不应混淆的边界 |
|---|---|---|
| 负责人（Owner） | 业务事实、明确授权与需要人作出的决定 | agent 自己的推断不能替代人的授权 |
| 舰长 | 定任务、选舰员、收单、组织复审、作验收判断、按授权推进并线和部署 | 不包办业务代码；规程要求将施工派给舰员 |
| 舰员 | 在任务允许的工作区施工，交 PASS / FAIL / BLOCKED 回执及证据 | 交回执不等于已验收、已合并或已上线 |
| 复审舰员 | 对指定锚点和判据独立复核 | 不能只复述承建者的结论 |
| 脚本与监听 | 登记、发现状态变化、通知、复放可机械判断的检查 | 没有证据时不能替模型或人编一个“成功” |

规程中的正式实例、不可逆动作和外部沟通有单独边界；交接、回执、监听配置也必须脱敏。详见 [总规程][S1] §0–§3、§5–§8。

### 三类状态，不要混成一个绿勾

1. **任务状态**：激活器只有「待开工 / 施工中 / 已完成」；阻塞写 `blocker`，证据写 `evidence`。
2. **投递结果**：忙、限流、草稿、未确认、已送达、已排队、已确认重复，不是同一个意思。脚本退出码 `0` 也可能是排队或重复确认。
3. **回执结论**：PASS / FAIL / BLOCKED。舰长验过实物才决定是否收单，是否并线、部署还要分别过门。（[总规程][S1]、[激活器规格][S3]、[投递参考实现][S5]）

## 一张单怎样形成证据闭环

**下面是按现有规程整理的流程示例，不是一段声称已完整复现的真实运行录像。**

| 阶段 | 动作 | 留下什么，怎样知道下一步能走 |
|---|---|---|
| 1. 写任务书 | 舰长列目标、读取/写入范围、工作区、判据、回执位置 | 任务书文件；明确哪些不做、什么情况下判 FAIL |
| 2. 登记与选通道 | 在激活器登记；辨认工具、终端、目标会话 | 任务号、owner、任务书/回执引用；会话来自清单，不凭短号猜 |
| 3. 投递 | 用适合该会话的通道发送 | 规格要求输入行空闲、写入、读回本条关键词、再提交并确认；当前参考实现尚未按此顺序独立验收，见下方限制与醒目提示 |
| 4. 遇忙或权限阻塞 | 保留未送达/未确认事实，先分清草稿、工作中、问题框还是审批 | 不把失败改写成成功；不自动替人批准，也不换通道绕过拒绝。需要人时保持 BLOCKED、等用户批准，并继续不受影响的工作 |
| 5. 施工与回执 | 舰员按范围完成，不能完成也交回执 | PASS / FAIL / BLOCKED、提交锚点、验证输出、剩余风险；回执监听通知舰长 |
| 6. 舰长验收 | 看实物、对照判据，安排独立复审 | 更新激活器与证据；不通过则返工或保持受阻 |
| 7. 并线、部署与交接 | 分别执行门禁、授权、回退和收尾规程 | 并线锚、版本真相、业务心跳或交接卡；不是“agent 回了完成”就上线 |

依据：[任务书模板](templates/01-任务书.md)、[回执模板][S6]、[终端投递规格][S2]、[激活器规格][S3]、[总规程][S1]。

- **L4 · Cursor / agy 专用经验**：`LOCAL/crew/dispatch-matrix.md`、`LOCAL/tools/cursor-say.py`。短消息指针、忙时处理、目录沙箱与模型故障等。

## 当前可以先用什么

### 1. 先看只读舰队看板，不接真实舰队

在取得仓库源码后，从仓库根目录运行：

```bash
python3 scripts/fleet-board/server.py --demo
```

这条命令来自看板说明的演示入口。它使用仓库内 **Sample Data（样例数据）**，不读取真实舰队目录；服务打印回环地址，默认端口 `8765`。**本文起草时没有重新运行它。** `--demo`、默认端口与回环绑定已在源码接口核对。（[只读看板说明][S4]、[看板服务入口][S10]）

现有页面能看：谁在做什么、任务书和回执所形成的往来、未答问题；可选显示窗口快照和管家水位。它不能派单、批准、往终端打字或替舰长验收；往来主要由现有字段和文件时间推导，不是完整的投递审计流。（[只读看板说明][S4]）

### 2. 接一张真实任务，先配环境与边界

这不是 `npm install` 后全自动接入的框架。先让负责指挥的会话读 [总规程](skill/SKILL.md) 的上任顺序，再按 [环境变量说明](scripts/README-env.md) 配置。以下使用该文档给出的**示例目录**，不是任何人的真实运行目录。（[总规程][S1]、[环境变量说明][S8]）

> **投递限制（请先读完再向真实会话发消息）。** [终端投递规格][S2] 要求：写入输入区后，先读回本条关键词，确认无误再补回车。当前仓库里的参考实现 `scripts/send-to-session.sh`（macOS + iTerm2，提交 `23c02a09ed`）是先写入并提交，再读屏核对。这一差异尚未按规格做独立验收。在完成独立验收之前，不要把该参考实现用于共享输入区或敏感会话。此处只说明限制，不修改脚本；详细对照在证据包，不在本页展开行号。

```bash
export FLEET_HOME="$HOME/fleet-data"
mkdir -p "$FLEET_HOME"
```

然后：

1. 运行 `bash scripts/terminal-probe.sh`，辨认终端与可用通道；按投递规格核实目标会话，不盲发。这个探测器仅检查环境与命令存在，不证明目标会话可送达。（[终端探测脚本][S12]）
2. 用 [任务书模板](templates/01-任务书.md) 写一张有范围、判据和回执路径的任务。
3. 用激活器登记任务；环境文档给出的最小登记示例是：

```bash
python3 scripts/task-activator.py add T1 "第一条任务" --owner 舰员乙
python3 scripts/task-activator.py list
```

4. 由舰长按通道派给一个舰员；收回执，核证据，再作验收。`add` 只是登记，**不会因此启动所有平台或自动执行这张单**。这里的 `add` / `list` 已核对公开源码参数声明，未实际执行。（[总规程][S1]、[终端投递规格][S2]、[激活器规格][S3]、[环境变量说明][S8]、[激活器命令声明][S11]）

若只想让看板读取你已准备好的舰队目录，使用 `python3 scripts/fleet-board/server.py`（不带 `--demo`）；它要求 `FLEET_HOME`，仍是只读页面。（[只读看板说明][S4]、[看板服务入口][S10]）

**OpenCode 适配另走一条线。** 请先读 [适配 README](adapters/opencode/README.md) 的 Host Registration 与 Safe Use。`npm ci` 只安装其依赖，不能当成宿主插件注册或 `/starfix` 安装成功。其公开验证记录限定了模拟回归、私有输入和真实 native/model 测试的范围。（[OpenCode 验证记录][S7]）

## 当前限制与已知对齐项

- **投递规格与参考实现不能混为一谈。** 规格要求回车前先读回本条关键词；当前参考实现是先提交、再读屏。在独立验收完成前，不要用于共享输入区或敏感会话。本页不改脚本。（[终端投递规格][S2]、[投递参考实现][S5]）
- **每家“成功”口径不同。** 本机包装中的 `SENT`、公开脚本中的 `DELIVERED/QUEUED`、回执 PASS、舰长验收，是不同层级。尤其 `SENT` 不能直接用作送达证据。
- **回执展示存在兼容口径待统一。** 激活器规格/模板用 PASS / FAIL / BLOCKED；看板说明描述按首条非空行的中文通过/失败/受阻识别。不要假定任意格式都能被所有组件一致识别。（[激活器规格][S3]、[只读看板说明][S4]、[回执模板][S6]）
- **只读看板不是可靠派单审计。** 它不读派单/收件箱流水；缺稳定角色字段时窗口不并入人物卡；没有舰长当前正在处理哪张单的独立字段。（[只读看板说明][S4]）
- **适配候选不是全平台验收。** OpenCode 的公开验证明确排除了若干原生持久化、完整关闭、宿主切换和真实业务集成承诺。（[OpenCode 验证记录][S7]）
- **保护边界不可因 fallback 放宽。** 审批、被拒绝动作和生产操作必须遵守授权；不复制本机凭据查询、权限放宽或人工审批绕行经验作为通用安装步骤。只有纯传输故障、备用通道已获准且工具允许，才讨论 fallback；权限拒绝保持 BLOCKED 等待用户批准。（[总规程][S1]）

## 下一步：外置驾驶舱（规划，尚未交付）

目标是**统一指挥，不统一运行环境**：一个可拖拽、可吸附的小浮窗，展开后看舰长与舰员关系、任务、阻塞、回执与验收，agent 留在原来的终端/应用中。

信件飞行动画只绑定真实事件：请求发出、已确认接收/排队、送达未确认、受阻、回执到达、验收通过分别显示。**点按钮不等于送达；回执飞回也不等于验收通过。** 当前看板的数据推导不足以支撑全部动画；还需要角色与会话映射、各通道证据语义、幂等/权限规则和可审计事件的对齐。

建议推进顺序（规划，不是已完成版本）：

1. 脱敏整理本机的分平台投递/fallback矩阵，先解决相互冲突的权限与忙时规则。
2. 将输入安全、去重、状态识别的本地改动做成可复现的候选，再独立验收。
3. 统一角色/会话、任务/回执、投递/验收的关联和事件语义。
4. 在现有只读看板基础上做小浮窗，再考虑受控派单和审批入口；不先承诺所有平台接管。
